# Changelog

This repository uses two version streams:

- `atoms-vX.Y.Z`: operation data, schema, package manifests, naming rules, and documentation consumed by `ptm-atomic sync`.
- `cli-vX.Y.Z`: CLI package code, command behavior, CLI error handling, and CLI packaging changes consumed by `uv tool upgrade ptm-atomic`.

The two streams are intentionally separate. A schema or operation-library change does not imply a CLI package release, and a CLI bug fix does not imply a new operation-library release.

- Add IPv6 DHCP server atom specs, adapter profile mappings, and allowlisted runner support: `fw_config_dhcpv6_server` (POST `/api/v1/dhcpv6`), `fw_update_dhcpv6_server` (PUT `/api/v1/dhcpv6`), `fw_disable_dhcpv6_server` (folded read-modify-write `PUT /api/v1/dhcpv6`), `fw_verify_dhcpv6_server` (GET `/api/v1/dhcpv6`), `fw_delete_dhcpv6_server` (DELETE `/api/v1/dhcpv6?id=<interface-name>`), `fw_verify_dhcpv6_static_ip`, and `fw_delete_dhcpv6_static_ip` (DELETE `/api/v1/dhcpstaticip?id=<binding-address>`), with the `run dhcpv6 config`/`update`/`disable`/`verify`/`delete`/`static-ip-verify`/`static-ip-delete` subcommands backed by `runner/dhcpv6.py` (dry-run by default, `--execute` for live device requests). The payload differs from the IPv4 family in three ways: `server.subnet` is a single CIDR string instead of a `subnets` array (no `range` pool, no `gateway`), `server.prefix` and `server.prefix_len` are two more required fields, and a static binding addresses its client by `duid` rather than by `mac`. `/api/v1/dhcpv6` answers its list under `data` where IPv4 uses `vals` — the only response-shape divergence between the two. `/api/v1/dhcpv6` is also the first endpoint in this repository whose failures arrive nested as `{"error": {"code", "message", ...}}` rather than flat; `_flatten_device_error` promotes the nested pair onto flat `errCode`/`errMsg` keys before the shared judgement runs, since that judgement reads flat keys only. Both `val.server.lease` and `val.server.subnet` are validated invariants: `lease` inherits the IPv4 isolation finding, and omitting `subnet` was proven locally on 2026-10-16 to crash the management service (nginx 502, roughly three minutes of outage, no session invalidation, no residual configuration), so a payload missing either key is rejected from any source including `--payload-json`. Device-side rules are deliberately not duplicated locally, because the runner performs no CIDR parsing: `subnet` must differ from `prefix` (`eDhcpdNetworkDuplicateWithDetail`), `prefix_len` must land in `[prefix length, prefix length + 16]` (`eDhcpdPrefixRangeErrorWithDetail`), and every binding address must fall inside `subnet` (`eDhcpdConfigHostIpWithinSubnetWithDetail`). Unlike IPv4 there is no rule that the subnet must sit on the interface's own network, `prefix` may equal it, and `prefix` is normalised on readback (`8888::1111/96` reads back as `8888::/96`). `ifmode` accepts `SERVER` only. A repeat delete, a never-existing interface name and an empty id all answer 400 `eRequestParam` with the message `http请求参数错误`, while a wrong method answers 405; because `eRequestParam` is a generic code, that code-and-message pair is registered in the new op-scoped `RESOURCE_NOT_FOUND_OP_CODE_MARKERS` table rather than in `RESOURCE_NOT_FOUND_ERR_CODES` or the global marker list, so the judgement cannot leak to another operation or misread a malformed request as goal-reached, and `validate_idempotent_registry` now rejects a marker entry whose op is not registered in `IDEMPOTENT_ERROR_TYPES`. A `DELETE` carrying no id at all answers 200 with a success body while leaving the configuration untouched, so the runner refuses an empty id before the request leaves. The static delete endpoint is shared with the IPv4 family and is extremely permissive — repeat delete, never-existing address and no id each answer 200 — so `fw_delete_dhcpv6_static_ip` is declared `idempotent: true` without `RESOURCE_NOT_FOUND` and is deliberately absent from `IDEMPOTENT_ERROR_TYPES`; the address is urlencoded (`:` becomes `%3A`) and differential probing confirmed the device decodes it and removes exactly the addressed binding.
- Add a dedicated DHCP disable operation to both families: `fw_disable_dhcp_server` (PUT `/api/v1/dhcp`) and `fw_disable_dhcpv6_server` (PUT `/api/v1/dhcpv6`), with the `run dhcp disable` and `run dhcpv6 disable` subcommands. Both are read-modify-write operations — `GET` the entry by interface name, replay it verbatim with `enable` false at both the `val` and `server` levels, then `PUT` it back — because live probing on 2026-10-16 proved no minimal body can disable a server: `enable`-only bodies were rejected with `eRequestParam` on their own and with `eDhcpdNoPrefixOrNetworkWithDetail` once the address pool was missing too. Round-trip probing showed the replay is lossless, with a key-by-key diff ignoring the enable flags coming back empty, and reversible; enabling again is an ordinary update, so no dedicated enable operation exists and each disable atom rolls back through its family's update operation. Both are registered in `IDEMPOTENT_ERROR_TYPES` with `RESOURCE_NOT_FOUND`, judged locally: an entry that does not exist means the interface had no DHCP service to disable, so the goal state already holds. `build_dhcp_server_val` also now emits a top-level `enable` key, fixing a live defect in the shipped IPv4 family — the device materialises `false` for an omitted top-level `enable`, so every static address deletion, which replays the entry, had been silently disabling the server.
- Add IPv4 DHCP server and static address binding atom specs, adapter profile mappings, and allowlisted runner support: `fw_config_dhcp_server` (POST `/api/v1/dhcp`), `fw_update_dhcp_server` (PUT `/api/v1/dhcp`), `fw_verify_dhcp_server` (GET `/api/v1/dhcp`), `fw_delete_dhcp_server` (DELETE `/api/v1/dhcp?id=<interface-name>`), `fw_verify_dhcp_static_ip`, and `fw_delete_batch_dhcp_static_ip`, with the `run dhcp config`/`update`/`verify`/`delete`/`static-ip-verify`/`static-ip-delete-batch` subcommands backed by `runner/dhcp.py` (dry-run by default, `--execute` for live device requests). A DHCP server is identified by the interface it binds to, so `val.ifname` is also the delete `?id=` value and the update body id. `POST /api/v1/batchv2` is the repository's first batch endpoint outside `/api/v1/batch`: it takes the same payload shape but answers with per-item `id`/`data` keys instead of `status`/`msg`, so `runner/batch.py#summarize_batch_result` is deliberately not wired for this family — it reads only `status`/`msg`/`message`/`errMsg`, which would judge every item indeterminate, downgrade the whole batch, and leave `success_count`/`failed_count` permanently `null`. The endpoint is documented in `docs/API-ADAPTER-SPEC.md`. Four live findings drive the contract. First, `POST /api/v1/batchv2` honours only the **first** element of a multi-element `body.id` list: measured on 2026-10-13, one item carrying `["8.1.1.101", "8.1.1.102"]` deleted `8.1.1.101` alone, answered a single `BatchResult` entry, and left `8.1.1.102` in place with no error — a silent partial success. The family builder therefore passes `carrier="per_id_item"` to `build_batch_delete_payload` so each address gets its own item, overriding the shared builder's `single_item` default; the specification's own example body is a single-element `id`, consistent with the observed behaviour. Second, `val.server.lease` is a validated invariant, not a default: the interface specification marks it optional, but a single-variable isolation test on 2026-10-13 proved that a POST or PUT to `/api/v1/dhcp` without it crashes the device management service (nginx 502, roughly 90 seconds of outage, then sessions must be re-established), so the runner rejects a lease-less payload from any source including `--payload-json`. Third, a static host binding address must fall inside its subnet's `range` pool, not merely inside the subnet — the device answers `eDhcpdConfigHostIpInNet` (DHCP服务器保留IP应在地址池范围内) otherwise. Fourth, `/api/v1/dhcpstaticip` is delete-only (GET and POST answer 405) and has no storage of its own; static bindings are a projection of each DHCP entry's `server.hosts` and vanish with the server that declares them, so `fw_verify_dhcp_static_ip` reads `/api/v1/dhcp` and emits one `{ifname, name, addr, mac}` row per binding. Separately, the DHCP query endpoint supports no filtering or pagination: seven candidate parameters (`key`, `keywords`, `name`, `ifname`, `page`, `size`, `search`) were each measured as silently ignored on 2026-10-13, so the two query operations expose no query flags rather than a non-functional one. `fw_delete_dhcp_server` is registered in `errors.py#IDEMPOTENT_ERROR_TYPES` with `eDhcpdConfigGetFail`, a dedicated `eDhcpd*` code the device returns for a repeat delete, so cleanup steps stay idempotent. Every scalar CLI flag on this family uses `action="append"` with `_single_arg`, so a repeated flag such as `--subnet a --subnet b` fails loudly with `RUNNER_VALIDATION_FAILED` instead of silently letting the last value win; multiple subnets must go through `--payload-json`, because a payload tree this deep cannot be expressed by index-aligned parallel flags.
